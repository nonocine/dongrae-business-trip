# 전화 공결 증빙 — 학부모가 앱에서 올림 (동래방카 요청 5번)

> 2026-10-28 설계(코드 수정 전). 요청 원문: 동래방카 저장소 `docs/REQUESTS_조유경_20261027.md` 5번.
> 관장 결정: 전화로 공결을 받아도 서류는 갖춰야 한다. 학부모가 앱에서 증빙을 올리고,
> 팀장 결재는 증빙이 올라온 뒤에만 가능.
> DB 변경: `supabase/migrations/bk_absence_phone_evidence.sql` (작성만, 실행 전)

## 1. 지금 구조

### 표 (운영 DB 실측, 2026-10-28)

`bk_absences` — 공결 한 건
- 신청 내용: `student_id`, `start_date`·`end_date`, `reason_type`(family·illness·religion·school·academy·care·other), `reason`
- 확인자: `confirmer_type`(guardian·teacher·other), `confirmer_other`, `confirmer_name`, `guardian_id`, `signature_path`(보호자 서명 PNG)
- 경로: `channel`(app·phone), `received_by`(전화 받은 직원)
- 처리: `status`(submitted·teacher_checked·approved·rejected·cancelled, **CHECK 제약**), `teacher_checked_by/at`, `approved_by/at`, `reject_reason`, `confirmed_on`
- RLS 켜짐 + 정책 없음 → 두 앱 모두 서버(service_role)로만 읽고 씀. 트리거 없음.

`bk_absence_files` — 증빙 파일(`absence_id` → `bk_absences` ON DELETE CASCADE, `path`·`name`·`mime`·`size`)
- 파일은 비공개 버킷 `bangka-media` 의 `absences/{공결 id}/…`. `absence_id` 인덱스 없음.

운영 데이터: 앱 신청 1건(결재 완료, 증빙 있음), **전화 공결 1건(10-27, 결재 완료, 증빙 0개)**.

### 흐름

| | 앱 신청(학부모) | 전화 공결(직원) |
|---|---|---|
| 입력 | 동래방카 `/more/absence/new` → `POST /api/absence` | 동업자씨 `/bangka/absences?view=phone` → `createPhoneAbsence` |
| 필수 | 자녀·기간·사유 + **보호자 서명** + **증빙 1개 이상**(최대 5개·합계 4MB) | 학생·기간·사유 |
| 확인자 | 보호자(본인, 서명) | 선생님(받은 직원) |
| 시작 상태 | `submitted`(접수) | **`teacher_checked`(곧바로 담임 확인)** |
| 다음 | 담임 확인 → 팀장 결재 | 팀장 결재(증빙 없이도 가능 ← 이번에 막을 곳) |

- 직원은 이미 공결 건에 증빙을 덧붙일 수 있음(`createAbsenceFileUpload`·`finalizeAbsenceFile`).
- 학부모 공결 목록(`/more/absence`)에는 전화 공결도 "전화" 배지로 보이지만, 할 수 있는 일은 없음(접수 단계 본인 신청 취소만).
- 공결확인서 PDF: 전화 공결은 확인자 = 받은 직원 이름, 서명 칸 비움.

## 2. 상태 흐름 (제안)

```
전화 공결 입력 ──▶ evidence_pending(증빙 대기) ──학부모 증빙 업로드──▶ submitted(증빙 제출됨)
                        │                         (또는 직원이 종이 서류를 대신 올림)
                        └─ 반려·취소(직원) ─▶ rejected / cancelled
submitted ──담임 확인──▶ teacher_checked ──팀장 결재──▶ approved
```

- 새 상태는 **`evidence_pending` 하나만** 추가. 증빙이 올라오면 기존 `submitted` 로 넘겨,
  담임 확인 → 팀장 결재는 앱 신청과 똑같은 길을 탑니다(기존 상태 전이 코드 재사용).
- 화면 이름표

  | status | 직원(동업자씨) | 학부모(동래방카) |
  |---|---|---|
  | evidence_pending | 증빙 대기 | **증빙 필요** |
  | submitted + channel=phone | **증빙 제출됨** | 확인 중 |
  | submitted + channel=app | 신청 | 접수 |
  | 그 밖 | 지금 그대로 | 지금 그대로 |

- 담임 확인을 전화 받은 직원이 이미 한 셈이라도, 서류를 본 뒤에 확인하는 것이 맞으므로
  증빙 제출 뒤 담임 확인을 다시 거칩니다(앱 신청과 같은 2단계).
- **증빙 없는 담임 확인·결재 금지**: 서버 액션에서 먼저 막고(친절한 문구), DB 트리거로 한 번 더 막음
  (상태가 teacher_checked/approved 로 바뀌는 순간 증빙 0개면 오류). 앱 신청은 원래 증빙 필수라 영향 없음.

## 3. 학부모 앱 (동래방카)

### 공결 목록 `/more/absence`
- `evidence_pending` 건: 노란 "증빙 필요" 배지 + 카드 안 큰 버튼 **[증빙 서류 올리기]**
  + 한 줄 안내 "전화로 접수된 공결입니다. 진료확인서·안내문 사진을 올려 주세요."
- 이미 결재된 옛 전화 건 중 증빙 요청된 건(`evidence_requested_at` 있음 + 파일 0개)도 같은 버튼(6장 A안).
- 첫 화면(홈)에도 증빙 필요 건이 있으면 한 줄 알림(눌러서 목록으로) — 이번 범위에 넣을지 선택.

### 업로드 화면 `/more/absence/{id}/evidence` (새 화면)
- 위: 공결 요약(자녀·기간·사유, "전화 접수: ○○○ 선생님") — 읽기만.
- 사진·PDF 고르기 — 앱 신청과 같은 규칙과 부품(브라우저에서 긴 변 1600px JPEG 로 줄임, 최대 5개·합계 4MB).
- [제출] → `POST /api/absence/{id}/evidence`
  - 로그인 보호자의 연결된 자녀 건인지, `channel=phone` 이고 `evidence_pending`(또는 6장 A안의 옛 건)인지 확인
  - 파일 내용으로 형식 재확인(지금 신청 API 의 sniff 그대로), `absences/{id}/` 에 올리고 `bk_absence_files`
    (`uploaded_by`=보호자 이름, `uploaded_by_guardian_id`) 기록
  - `evidence_pending` → `submitted`, `evidence_submitted_at/by` 기록(동시 제출은 상태 조건부 update 로 한 번만)
  - 실패 시 올린 파일 지움(신청 API 와 같은 정리)

### 서명은? — **받지 않는 것을 제안**
- 앱 신청의 서명은 공결확인서 "확인자: 보호자 (인)" 칸을 채우기 위한 것(확인자 = 보호자).
- 전화 공결은 확인자가 **받은 선생님**이고 공결확인서도 그 이름으로 나감 → 보호자 서명이 들어갈 칸이 없음.
  증빙은 "서류 첨부"일 뿐이라 서명을 더 받으면 학부모 부담만 늘어남.
- 누가 올렸는지는 `uploaded_by_guardian_id`·`evidence_submitted_by`·시각으로 남음.
- (대안) 관장님이 "보호자 확인을 받아야 한다"고 보시면: 업로드 화면에 서명 칸을 넣고, 서명하면
  확인자를 보호자로 바꿔 공결확인서도 보호자 서명으로 출력. → 결정 필요(아래 8장).

## 4. 직원 화면 (동업자씨 `/bangka/absences`)

- 전화 공결 입력 → 바로 `evidence_pending`(받은 직원은 `received_by` 에 그대로, 담임 확인 칸은 비움).
  저장 뒤 안내 "학부모 앱에 '증빙 서류를 올려 주세요'가 표시됩니다."
- 목록
  - "처리할 공결" 탭: `submitted`(앱 신청 + 증빙 제출된 전화) · `teacher_checked` — 지금 그대로
  - 새 묶음 **"증빙 대기"**(`evidence_pending` + 증빙 요청된 옛 건): 학부모 응답을 기다리는 건이라
    상단 배지(처리할 공결 수)에는 넣지 않고 따로 숫자 표시. 며칠째 대기인지(`evidence_requested_at`) 표시.
  - 카드 배지: "증빙 대기"(노랑) / "증빙 제출됨"(파랑) / 증빙 0개면 "증빙 없음"(빨강)
- 버튼
  - 증빙 0개면 **[담임 확인]·[팀장 결재] 비활성** + "증빙 서류가 올라와야 처리할 수 있습니다" 문구
  - 학부모가 종이로 가져온 경우: 직원이 [증빙 올리기](이미 있는 기능)로 올리면 `evidence_pending` → `submitted`
    (`evidence_submitted_by` = 직원 이름) — 이후 같은 흐름
  - 증빙 대기 건도 반려(사유) 가능 — 지금 반려 규칙 그대로(담당자 누구나)
- 공결확인서 PDF: 바뀌는 것 없음(확인자 = 받은 직원). 증빙은 지금처럼 뒤 장에 붙음.

## 5. 두 앱 공통으로 맞출 코드값

`lib/bangkaAbsence.ts`(동업자씨) ↔ `lib/absence.ts`(동래방카): `AbsenceStatus` 에 `evidence_pending`,
상태 이름표, 각자 주석의 흐름 설명. 상태 배지 색(학부모 앱 `BADGE`)도 추가.

## 6. 이미 들어간 전화 공결(운영 1건: 10-27, 결재 완료, 증빙 0개)

- **A안(추천)**: 결재는 그대로 두고 "증빙 요청"만 표시(`evidence_requested_at`). 학부모 앱에 같은 버튼이
  뜨고, 올리면 서류만 붙고 상태는 그대로. 직원 목록 "증빙 대기"에 "결재됨·증빙 없음"으로 보임.
  → 결재 기록(누가 언제)을 고치지 않아 이력이 깨끗함. SQL 5-b.
- B안: 결재를 되돌려 `evidence_pending` 으로(결재 기록 지움). 규칙엔 더 맞지만 이미 끝난 결재를 지움.
  SQL 안에 주석으로만 넣음.
- 결재 전 전화 공결 중 증빙 없는 건은 `evidence_pending` 으로 옮김(SQL 5-a, 현재 0건).

## 7. 순서

1. SQL 실행(관장님 MCP) — 기존 화면은 그대로 동작, 증빙 없는 결재만 DB 가 막음.
2. 동업자씨: 상태값·전화 입력 시작 상태·목록 "증빙 대기"·버튼 막기·직원 대신 업로드 시 상태 넘김.
3. 동래방카: 상태값·목록 버튼·업로드 화면·`POST /api/absence/{id}/evidence`.
4. 두 앱 같이 배포(상태값이 한쪽만 알면 다른 앱에서 "알 수 없는 상태"로 보이므로 같은 날).
5. 확인: 전화 공결 입력 → 학부모 계정으로 증빙 올리기 → 직원 담임 확인·결재 / 증빙 없을 때 버튼·DB 막힘.

## 8. 결정이 필요한 것

1. 업로드할 때 보호자 서명 — 받지 않음(제안) / 받아서 확인자를 보호자로 바꿈
2. 운영 1건 — A안(제안) / B안
3. 증빙 대기 알림 — 학부모 홈 한 줄 알림까지 할지(요청 10번 업무시간 규칙과는 무관: 학부모 쪽 업로드는
   공결 신청처럼 언제나 가능하게 제안)
4. 증빙 대기가 오래되면(예: 7일) 직원 목록에서 강조할지
